# 세로 넘침 두 가지 — 거대 PNG와 columns 안 박스 개수

## `savefig(bbox_inches="tight")`가 만든 초대형 PNG → `Dimension too large`

**증상** `! Dimension too large. <argument> \ht \@tempboxa`가 그 프레임의 `\end{frame}`에서 보고되고, 같은 프레임에 `Overfull \vbox (3822pt too high)`. PDF는 나오지만 해당 페이지가 깨진다.
**원인** tight bbox는 **축 밖에 놓인 텍스트·주석까지 포함**해 bbox를 잡는다. 데이터 범위가 극히 좁은데(예: 0.4995~0.5000) 주석 y를 범위 밖(0.42)에 두면 그림 높이가 수백 인치로 폭발 → PNG가 `1286x47952` 같은 크기가 되고, `\includegraphics[width=...]`의 환산 높이가 TeX 한계(≈19 feet)를 넘는다.
**해결** 그림 생성 직후 크기를 검사하고, 비정상 그림은 주석 좌표를 데이터 범위 안으로 옮기거나 `ax.set_ylim`을 명시한다.
```bash
magick identify figs/*.png | awk '{print $3, $1}' | sort -t x -k2 -rn | head
```
데이터가 뭉개져 범위가 좁아지는 흔한 원인: sklearn `staged_decision_function`이 `(n,1)`을 돌려주는데 `(s > 0) == y_true`로 비교하면 `(n,n)`으로 브로드캐스트돼 정확도가 전부 ≈0.5가 된다 → `np.ravel(s)`로 편다.

### 같은 폭발의 변형: 값이 전부 동일한 히스토그램(축 범위 0)
`plt.hist(scores)`의 `scores`가 **전부 같은 값**이면 x 범위가 0이라 tight bbox가 가로로 터진다(예: `1504x448` → `3779x487`). 컴파일 에러는 없고 슬라이드에서 그림만 납작해진다.
원인은 대개 **데이터가 너무 쉬워 모든 시행이 같은 답**을 낸 것이다(예: 잘 갈라진 블롭 3개에서 k-평균 초기화를 60번 바꿔도 WCSS가 전부 동일). 그림이 보여 주려던 "초기화에 따라 결과가 달라진다"도 함께 거짓이 된다 → **더 어려운 데이터로 바꾼다**(군집 수를 늘리고 분산을 키운다). 임시방편이 필요하면 `ax.set_xlim(v*0.9, v*1.1)`.

## beamer `columns` 안 tcolorbox는 열당 3개까지

**증상** 컴파일 에러 없이 마지막 박스가 footline을 덮거나 아래가 잘림. 로그에는 `Overfull \vbox (50~90pt too high)`만.
**원인** 열 하나의 실질 높이 예산은 **약 5.5cm**다. 타이틀 있는 `\scriptsize` 2줄 박스 하나가 약 1.4~1.6cm이므로 **4개면 넘친다**(3개는 안전).
**해결** 열당 박스 3개 이하로 유지한다. 넘치면 박스를 합치거나, 전체폭 박스로 내리지 말고(그쪽이 더 높다) 한 줄 평문 `{\scriptsize ...\par}`으로 바꾼다.

### 열당 4개가 꼭 필요할 때
박스 본문이 **정말 한 줄**(0.49열 = 약 5.8cm에 `\scriptsize` 기준 한글 26자 이내)이고
박스 사이 간격을 `\vspace{0.02cm}`로 줄이면 4개까지 들어간다. 본문이 두 줄로 감기는 순간
다시 넘치므로, 줄바꿈 여부를 렌더해서 확인한다.

## 종횡비 1.4~2.2 그림에 `width=0.9\textwidth`를 주면 거의 항상 넘친다

**증상** `Overfull \vbox (30~150pt too high)`. 슬라이드 마지막 tcolorbox가 통째로 사라지거나
footline을 덮는다. 그림 자체는 멀쩡해 보여서 원인을 그림으로 의심하지 않게 된다.
**원인** 번들 규칙 「가로>2:1이면 `width=`」의 경계 바로 아래 구간이 위험하다.
`width=0.9\textwidth` ≈ 10.7cm 이므로 환산 높이는 **10.7 / 종횡비** cm다.
종횡비 1.4 → 7.6cm, 1.8 → 5.9cm, 2.0 → 5.4cm — 콘텐츠 예산 7.0cm를 그림 하나가 다 쓴다.
**해결** 그림 + 박스가 같이 있으면 **환산 높이를 먼저 계산**하고 남는 예산으로 폭을 정한다.
```
쓸 수 있는 폭 W(\textwidth 배수) = (원하는 높이 cm x 종횡비) / 11.9
예: 종횡비 1.5 그림을 3.0cm로 → W = (3.0 x 1.5) / 11.9 = 0.38
```
종횡비가 2.2 미만이면 애초에 `height=`로 지정하는 편이 예산 계산이 쉽다.
단 columns 안에서는 `height x 종횡비 <= 열 폭`인지 반드시 검산한다(위 항목 참조).

## 오버플로를 고치려고 `columns`를 세로로 풀면 **더 넘친다**

**증상** 넘치는 프레임에서 2열 `columns`를 없애고 박스를 위아래로 쌓았더니 `44pt` → `61pt`로 악화.
**원인** `columns`는 두 박스를 **같은 세로 구간**에 놓는다(높이 = 둘 중 큰 쪽). 풀면 높이가 **합**이 된다. 열 폭이 좁아 줄 수가 늘어난 것보다, 세로로 쌓인 손해가 훨씬 크다.
**해결** 방향이 반대다 — `columns`는 **유지**하고, 아래쪽 전체폭 박스의 **개수를 줄인다**(합치기). 넘치는 프레임의 예산은 보통 `columns 1개 + 전체폭 박스 2개`가 상한이다.
```latex
% 위험: columns 제거 -> 세로 합산
% 안전: columns 유지 + 아래 박스 3개를 2개로 합치기(\\ 로 문단 이어붙이기)
```
**일반 규칙** 가로로 나란한 것을 세로로 바꾸는 수정은 **항상 높이를 늘린다**. 오버플로 수정은 "박스 수 줄이기 → 폰트/여백 줄이기 → 프레임 분리" 순서로 시도한다.
